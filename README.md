# I2C_MemoryMap ツール

Saleaeのロジックアナライザ(Logic 2アプリ)で取得したI2C通信ログ(CSV)を読み込み、I2Cデバイス毎のレジスタ空間（Write / Read別）の遷移をImGui上のメモリビューアで視覚的に解析・再生するためのツールです。

---

## 📁 フォルダ構成

配布パッケージ内には以下のファイルが含まれています。

* **`i2c_memorymap.exe`** : メインプログラム
* **`devices/`** : デバイス定義ファイル（JSON）を格納するフォルダ
* **`sample_CSV/`** : サンプルデータ置き場
* **`saleae-live/`** : Logic 2 のライブ受信用拡張機能

---

## 🛠️ 使い方

### 1. デバイス設定の配置 (`devices/` フォルダ)

デバイス設定を使う場合は、バスが1個の場合も `devices/<バス名>/` フォルダを作成し、その直下にデバイス設定ファイル(JSON)を配置してください。例えば、バス名が `I2C` なら `devices/I2C/` に配置します。各バスフォルダ直下のすべての JSON ファイルを、そのバスの設定として読み込みます。JSONの詳しい記述仕様は**付録**を参照してください。

デバイス設定は省略できます。`devices/` フォルダや対応するバスの JSON ファイルがなくても起動でき、未定義のバス・デバイスは通信から自動登録されます。この場合は既定の設定（レジスタアドレス1バイト、アドレス自動インクリメントあり）で解析するため、実際のデバイス仕様に合わない場合は JSON を用意してください。設定を省略しても、バスは CSV のデコーダ名または Live Bridge のバス名で区別されます。

#### バス名とフォルダ構成

`devices` 直下のフォルダ名がバス名です。各フォルダ直下の JSON ファイルは、すべてそのバスのデバイス定義として読み込みます。JSON 内にバス名を書く必要はありません。

```text
devices/
├─ I2C/
│  ├─ eeprom.json
│  └─ sensor.json
└─ I2C [1]/
   └─ controller.json
```

1個のCSVを読み込み、先頭列のアナライザー名（例：`"I2C"`、`"I2C [1]"`）をバス名として使います。フォルダ名と大文字・小文字を含めて一致させてください。各バス内では時刻順を保ち、バス間の行は混在して構いません。同一時刻の行はCSV内の順序で処理します。時刻は全バス共通の時計・起点を使ってください。

同じアドレスでもバスが違えば独立したデバイスです。STOPはそのバス内だけに作用します。画面の選択時刻は共通で、各デバイスは選択時刻以下の最新状態を表示します。統合タイムラインの `Bus / I2C Address` 列でバス名も表示・絞り込みできます。

未定義のバス・アドレスは既定のデバイス設定で自動登録します。同一バス内のアドレス重複定義はエラーになります。バスフォルダ内のサブフォルダは読み込みません。

ライブ受信も複数バスに対応します。各 Live Bridge の `Bus name (match folder name under devices; blank = I2C)` に、対応するデバイス定義フォルダと同じバス名を設定してください。空欄は `I2C` になります。

### 2. I2Cログファイル取得

CSVを出力する前に、Logic 2の各I2Cデコーダ（アナライザ）の名前を、`devices` フォルダ直下の対応するフォルダ名と一致させてください。例えば、`devices/I2C/` を使うバスは `I2C`、`devices/I2C [1]/` を使うバスは `I2C [1]` に設定します。CSVに出力されるデコーダ名をバス名として使うため、大文字・小文字や空白も含めて一致させる必要があります。

Logic 2アプリからI2CログのCSVファイルを出力します。出力時の設定は以下に合わせてください。

* **`Columns`**: All
* **`Data`**: 任意
* **`Export Format`**: CSV
* **`User ISO8601 Timestamps`**: 使用する（絶対時刻を保持する場合）
※確認時点のLogic 2アプリバージョン 2.4.46

### 3. 起動とCSVファイル選択

1. **`i2c_memorymap.exe`** をダブルクリックして起動します。
2. 起動直後にファイル選択ダイアログが開くため、解析したい **I2CログのCSVファイル** を選択します。
サンプルのCSVは`sample_CSV`フォルダにあります。
3. ウィンドウが立ち上がり、タイムライン操作や各デバイスのWrite/Readメモリマップの確認が行えるようになります。

### Logic 2 リアルタイム受信

1. Logic 2 の Extensions から、このリポジトリの `saleae-live` フォルダをローカル拡張機能として追加します。
2. Logic 2 にバスごとの I2C アナライザを追加し、それぞれを入力にして `I2C MemoryMap Live Bridge` を1個ずつ追加します。各 Bridge の `Bus name (match folder name under devices; blank = I2C)` に `I2C`、`I2C [1]` など別々の名前を設定してください。入力アナライザ名は自動取得しないため、CSV と揃える場合も手動で指定します。名前は大文字・小文字や空白を区別し、日本語・カンマも使えます（UTF-8で最大1,024バイト）。同時に使う Bridge 同士で同じバス名を設定しないでください。
3. 本ツール起動時の選択画面で **Yes** を選びます。Logic 2 のキャプチャ中に受信したデータが表示されます。**No** は従来の CSV 読み込みです。

拡張機能は `127.0.0.1:48151` に UDP でフレームを送ります。本ツールと Logic 2 は同じ PC で実行してください。ライブモードでは最新のデータへ表示位置が追従します。UDP のため、受信側が起動していない間のデータや、受信しきれなかったデータは再送されません。
複数 Bridge はすべて同じ受信ポートへ送信するため、バスごとにポートを変更する必要はありません。MemoryMap の受信アプリは1個起動してください。同じ Logic 2 キャプチャ内の各バスは共通時刻のタイムラインで表示します。
Logic 2 でキャプチャを停止して再開すると、各 Bridge の最初のフレーム受信時に、そのバスの履歴を初期化します。他のバスの履歴は消去しません。新しいキャプチャでフレームが届かないバスには以前の履歴が残ります。
CSV とライブ受信の時刻は UTC の Unix ナノ秒で保持します。CSV は `2026-09-22T08:20:18.204048396+00:00` のような ISO 8601 形式に対応します。Control Panel の `Time format` で UTC または PC のローカルタイムゾーン（夏時間を含む）の ISO 8601 表示、日付を省いた短縮表示、先頭イベントからの経過秒を選べます。標準はローカル時刻の短縮表示です。どの時刻表示もナノ秒まで示し、ローカル表示は時差表記を付けずに変換済みの時刻を示します。CSV 読み込み時は `CSV original` で元ファイルの時刻文字列をそのまま表示できます。経過秒の基準はキャプチャ開始時刻ではなく最初のデータイベントです。旧形式の数値秒 CSV も読み込めますが、絶対時刻は含まれません。`Go to nearest transaction` は Control Panel の時刻表示選択欄の近くにあり、選択中の表示形式で入力できます。ジャンプ欄は最初のデータ時刻で初期化され、タイムラインで選択を変えても入力値を保持します。短縮形式の日付は最初のデータ時刻に最も近い日として解釈します。
ライブ画面の Control Panel に UDP フレームの受信件数と連番の欠落件数を表示します。連番はバスごとに判定し、画面には各バスの現在のキャプチャの合計を表示します。リセット時は対象バスの件数だけを初期化します。欠落件数は次のフレームが届いた時に確定するため、最後のフレームだけが失われた場合や Logic 2 側でデコードされなかったデータは検出できません。
UDP 受信は専用スレッドで行い、最大 32,768 フレームのアプリ内キューへ積みます。画面側はキューからまとめて取り出して履歴を更新します。Control Panel にはキュー使用量、キュー満杯時の破棄件数、OS ソケット受信バッファの設定値を表示します。

### 4. 操作方法

* **タイムライン移動**: 画面下部のコントロールパネルにあるスライダー、または `<< Prev` / `Next >>` ボタンでタイムスタンプ単位のステップ移動が可能です。
* **キーボード操作**: キーボードの **← / → 矢印キー** でも前後のデータにすばやく移動できます。

## 📌 付録：デバイス定義 JSON 仕様詳細

`devices/` フォルダ内に配置するJSONファイルのフォーマットおよび各設定項目の詳細です。独自のデバイスを追加・定義する際にご参照ください。

#### デバイス定義 JSON のフォーマット例

```json
{
  "devices": [
    {
      "name": "HDCP_Port_Primary",
      "dev_addr_7bit": "0x3A",
      "reg_addr_bytes": 1,
      "endian": "little",

      // ▼ 動作モード・挙動制御
      "auto_addr_inc": false,
      "support_direct_read_from_default_reg": true,
      "default_reg_addr": "0x08",

      // ▼ レジスタマップ定義
      "registers": [
        {
          "address": "0x00",
          "name": "Bksv",
          "bits_read": [
            { "byte_offset": 0, "bit_offset": 0, "width": 8, "name": "Bksv[7:0]" }
          ]
        }
      ]
    }
  ]
}

```

#### 各設定項目の詳細

##### 1. 基本情報

* **`name`**: デバイスの表示名（ウィンドウタイトルやタブに反映されます）
* **`dev_addr_7bit`**: 7ビットI2Cアドレス（16進数文字列、例: `"0x3A"`）
* **`reg_addr_bytes`**: レジスタアドレスの幅（バイト数、`0`～`4`まで対応）
* **`endian`**: マルチバイトデータのエンディアン（ビット定義を行っている場合に適用されます。現在`"little"`のみ対応。）

##### 2. 動作モード・挙動制御 ⚙️

* **`auto_addr_inc`**: アドレスの自動インクリメントの有無（`true` / `false`、reg_addr_bytesが1以上の時に有効。メモリマップ的なデバイスは`true`、コマンドIDに複数バイト紐づくデバイスは`false`とする）
* **`support_direct_read_from_default_reg`**: アドレス指定なしのダイレクトリード時に特定アドレスのレジスタ値が読み出されるかどうか（`true` / `false`、通常のデバイスは`false`とする）
* **`default_reg_addr`**: ダイレクトリード時やリセット時に参照されるデフォルトアドレス（16進数文字列、support_direct_read_from_default_regが`true`の場合のみ有効）

##### 3. レジスタマップ定義 (`registers`)

デバイスが持つレジスタのリスト。各レジスタは以下のプロパティを持ちます。

* **`address`**: レジスタのアドレス（16進数文字列、例: `"0x00"`）
* **`name`**: レジスタの名称（例: `"Bksv"`, `"Ri'"`）
* **`bits`**: 読み出し（Read）、書き込み（Write）共通のビットフィールドの配列（省略可能）
* **`bits_read`**: 読み出し（Read）用ビットフィールドの配列（省略可能）。`bits`の定義よりも優先して適用されます
* **`bits_write`**: 書き込み（Write）用ビットフィールドの配列（省略可能）。`bits`の定義よりも優先して適用されます

##### 4. ビットフィールド定義 (`bits_read` / `bits_write`)

各レジスタ内に存在するビット単位・バイト単位のデータ構造を定義します。レジスタビュー上で、どの位置がどのデータに対応しているかを可視化するために使用します。

**ビットフィールドの各要素（オブジェクト）の構成:**

* **`byte_offset`**: レジスタ先頭からのバイトオフセット（例: `0` はレジスタの先頭バイト、`1` は次のバイト）
* **`bit_offset`**: 指定バイト内の開始ビット位置（`0`～`7`）
* **`width`**: ビット幅（例: 1バイト分なら `8`、複数バイトをまたぐ指定も可能です）
* **`name`**: 各ビットフィールドのラベル（例: `"Bksv[7:0]"` やステータスフラグ名など）

## 開発者向け：ビルドと配布物の生成

Windows では、通常の CMake ビルドに `distribution` ターゲットが含まれ、アプリ本体のビルド後に CPack が `dist/I2C_MemoryMap/` と `dist/I2C_MemoryMap.zip` を更新します。配布対象は `CMakeLists.txt` の `install()` で定義しています。Debug／Release ともに、そのビルドの実行ファイルを使用し、最後にビルドした構成で配布物を上書きします。リソースだけの変更・追加・削除も、次のビルドで反映されます。自動実行時はキー入力待ちやアプリ起動を行いません。`i2c_memorymap.exe` は終了してからビルドしてください。

```powershell
cmake --preset ninja-release
cmake --build --preset ninja-release-build
```

アプリと配布物だけを生成する場合は `cmake --build --preset ninja-release-build --target distribution` を使用します。`--target i2c_memorymap` を指定した場合はアプリ本体のみをビルドします。標準の `--target package` でも ZIP を生成できます。ZIP の直下には exe や `devices/` が入ります。

ビルド済みの成果物を再パッケージ化する場合は `cpack --preset ninja-release-package`（Debug は `ninja-debug-package`）を使用します。VS Code では `CMake: Select Package Preset` で構成を選び、Package を実行できます。
